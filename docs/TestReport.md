## 一、测试概述

### 1.1 测试目的

验证校园论坛系统各功能模块的正确性、性能指标、稳定性与安全性，确保系统在交付前满足需求分析文档中的功能性与非功能性要求，为项目评分中的"系统测试"维度（权重 20%）提供可量化的交付物。

### 1.2 测试范围

| 测试类型 | 覆盖范围 | 工具/框架 |
|:---------|:---------|:-----------|

| 功能测试（E2E） | 用户注册→登录→发帖→评论→点赞→通知→管理后台全链路 | Playwright |

## 四、性能测试

### 4.1 工具选型：Locust

选择 Locust 作为性能测试框架的理由：

| 对比项 | Locust | k6 | JMeter |
|:-------|:-------|:----|:-------|
| 脚本语言 | Python（与后端同栈） | JavaScript | XML / Groovy |
| 学习曲线 | 低（团队熟悉 Python） | 中 | 高 |
| 分布式压测 | 原生支持 | 需 Cloud 版 | 支持 |
| FastAPI 适配 | 优秀（同生态） | 良好 | 良好 |
| 实时监控 | Web UI 实时图表 | CLI + Grafana | GUI 图表 |

**结论**：Locust 与后端 Python 生态一致，脚本编写与维护成本低，Web UI 提供直观的实时监控，适合本项目规模。

> **性能拐点分析**：增压阶段（50→500），P95 从 730ms 快速上升，但进入稳态后回落至 86ms，说明系统存在短暂的请求排队现象，一旦连接池和工作线程预热完毕，性能趋于稳定。登录接口是明确的性能瓶颈，500 并发下 P95 达 680ms，与 argon2 计算密集特性直接相关。

### 4.6 性能瓶颈分析

#### 4.6.1 登录接口瓶颈

**现象**：登录接口 P95 在 500 并发下达到 680ms，远超 300ms 目标。

**根因**：登录接口使用 argon2 密码哈希算法进行密码验证。argon2 是一种计算密集型算法，每次验证耗时约 80-100ms。在 500 并发用户同时登录时，8 个 Uvicorn worker 的 CPU 资源被大量 argon2 计算占用，导致排队延迟。

**证据**：

- 基准(50并发) P95 = 120ms → 负载(200并发) P95 = 280ms → 压力(500并发) P95 = 680ms
- 响应时间增长与并发数近似线性关系，符合计算资源排队模型
- 500 并发下出现 1 次 HTTP 500 错误，表明资源竞争已导致偶发超时

**建议**：

1. 增大 Uvicorn worker 数量（当前 8，建议 16+）以分散 argon2 计算负载
2. 对 argon2 参数进行调优，降低 `time_cost` 或 `memory_cost`（在安全性与性能间权衡）
3. 实现登录接口限流（如令牌桶算法），避免大量并发登录请求同时涌入
4. 考虑在极端负载场景下使用 bcrypt（计算量较低但安全性略降）作为降级策略

#### 4.6.2 板块列表接口瓶颈

**现象**：板块列表 P95 在 500 并发下达到 140ms，超出 100ms 目标。

**根因**：板块列表接口在高压并发下存在以下问题：

1. **连接池竞争**：PostgreSQL 连接池大小为 20（overflow 30），500 并发请求同时竞争连接池资源
2. **冷启动效应**：部分请求在连接池建立新连接时产生额外延迟
3. **查询特点**：板块列表查询返回全量板块数据（无复杂筛选），但 P95 的偶发高延迟说明存在连接等待

**证据**：

- P50 始终保持在 4ms（连接池有可用连接时查询极快），但 P95 在高压下跳升至 140ms
- 压力测试中板块列表 P99 = 250ms，连接等待时间显著

**建议**：

1. 增大 PostgreSQL 连接池大小和 overflow 配置
2. 为板块列表添加 Redis 缓存（板块数据变更频率极低，适合缓存）
3. 考虑为板块列表增加短时间本地缓存（如 30s TTL）

#### 4.6.3 其他接口表现

其余接口（帖子列表、帖子详情、搜索、评论、通知）在所有并发级别下均表现稳定，P95 响应时间增长温和，表明：

- 数据库查询优化（索引、分页）效果良好
- FastAPI 异步框架在高并发下调度效率高
- 8 个 Uvicorn worker 对于读操作类接口已足够

### 4.8 性能测试总体评价

系统在 **200 并发用户以内** 所有性能目标均达标，满足校园论坛的正常运营需求。在 **500 并发用户（超负荷）** 条件下，系统仍保持稳定运行（错误率 0.012%、吞吐量 137.3 req/s），但登录和板块列表两个接口的 P95 超出目标值，属于可预期的性能降级行为。

核心瓶颈为 **argon2 密码哈希的计算密集性** 和 **PostgreSQL 连接池在高并发下的竞争**，通过增加 worker 数量、调优连接池配置和引入缓存策略可有效改善。
